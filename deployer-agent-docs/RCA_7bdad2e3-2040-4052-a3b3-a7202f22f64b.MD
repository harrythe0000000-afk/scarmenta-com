## Q4 — Do system probes still succeed while player launches fail?
No direct concurrent comparison is available: the last probe/auto-import run was at **12:10** (before the IP block began at 12:25), and it returned HTTP 200 (ok=True) on `launch.php` with the test user. No probe ran during the 12:25→13:25 403 window.

However the distinction the earlier RCA relied on no longer holds. Previously probes "succeeded" while launches "failed" only because the GGR error was a **business-level error returned with HTTP 200** (so the HTTP call succeeded). The current failure is a **transport-level HTTP 403** on `launch.php` — it is rejected before any user_id/balance is evaluated, so it would reject the probe user (`scm_test_9000000000`, balance 100.00) exactly as it rejects real players (`scm_<bulk_player_id>`, wallet_inr 95000). The parameter difference (test user/balance vs real user/balance) is therefore irrelevant to a 403. Note: `GET /api/v1/providers` (authenticated by api_key, not IP-gated the same way) still returned **200** at 12:19–12:24, which is why catalog sync keeps working while only the IP-gated `launch.php` is blocked.

## Root cause
The GGR recharge fixed the original issue (no GGR-depleted errors after 12:14:13). The current blocker is that InfinityAPI rejects the production deployment's outbound requests to `POST /launch.php` with **HTTP 403 IP_NOT_WHITELISTED**. Despite the user whitelisting an IP, the production cluster's actual egress/NAT IP (cluster `deployment-cluster-09`) is still not on InfinityAPI's allowlist for the launch endpoint — most likely the wrong IP was whitelisted, it was added to the wrong account/key, or it has not propagated. This is a third-party provider configuration issue; the app code is behaving correctly (it faithfully surfaces the provider's 403 as the 424 toast).

## Fixes
1. **User / third-party (InfinityAPI portal):** In InfinityAPI, open the operator/API-key config and confirm the IP allowlist for `launch.php`. Check InfinityAPI's own request/security logs for the **source IP of the blocked 403 requests** and whitelist exactly that IP. The IP they previously whitelisted is evidently not the IP these launch requests originate from.
2. **Emergent Support (to obtain the egress IP):** The app runs on a managed Kubernetes cluster (`deployment-cluster-09`); its stable outbound/NAT egress IP is platform-managed and not visible to the user. The user should raise an Emergent support ticket (quote deployment purple-credit / job b2a2a694-b6d0-4927-b2a6-e421a0415564) to get the deployment's outbound egress IP, then whitelist that exact IP at InfinityAPI.
3. **Code (minor, optional — E1):** The `infinity_ggr_alert` settings doc is not cleared/updated when the failure mode changes (still shows GGR-depleted from 12:14). Consider updating/clearing the admin alert to reflect the current provider error (e.g. IP_NOT_WHITELISTED) so operators aren't misled.

## What was NOT reproduced
This is a third-party provider + egress-IP configuration issue, not reproducible in a sandbox (no app secrets, different networking). Diagnosis is entirely from production logs (Loki, run 7bdad2e3) and the production MongoDB.
