## Conclusion
- The last observed failures were IP_NOT_WHITELISTED, but they are all PRE-deploy. There is no post-deploy launch data, so the whitelist cannot be confirmed working or broken yet.
- The app does NOT persist the rejected egress IP for IP_NOT_WHITELISTED, so neither the operator nor we can tell which IP(s) to whitelist or whether egress rotates — this is the real blocker to closing the loop.
- A separate GGR-depleted condition also blocks launches and is unaffected by whitelisting.

## Fixes
- **Code (E1):** In the live launch error handler, persist the FULL InfinityAPI response body for the IP_NOT_WHITELISTED branch (currently only the short `error` code is saved) into `live_sessions.reason`, and record the pod's own egress IP (the ipify value) on each failure + in the `infinity_ggr_alert`/settings doc (add `kind` and `ip` fields). Without this, the rejected IP is invisible. Also keep the original `Infinity launch rejected http=... error=...` log line.
- **User (test/verify):** Have a player actually retry a game launch now (hard refresh / incognito to drop any cached bundle), since no launch has reached the backend since 13:33:19Z. Then recheck live_sessions.
- **User (3rd-party):** Even with the IP whitelisted, the GGR-depleted errors (12:13Z) will still block those providers until the operator account is recharged at the InfinityAPI provider portal.
- **User (checks/decides):** Read the real egress IP via the authenticated `GET /api/admin/live/server-ip` and compare to the whitelisted value; if prod egress rotates across multiple IPs, a single whitelisted IP will keep failing — whitelist the full egress range.
