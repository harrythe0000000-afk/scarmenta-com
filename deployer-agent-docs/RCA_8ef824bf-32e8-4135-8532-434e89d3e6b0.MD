# RCA — scarmenta.com "Cloudflare could not parse response" (520) on login

## Reported symptom
Right after the latest deploy (run `8ef824bf`, promoted 2026-11-13 11:56 UTC), users report a Cloudflare error page when logging in: *"The origin web server sent a response that Cloudflare could not parse… empty response, malformed HTTP headers, or an otherwise invalid response"* (Cloudflare error 520). Already-known facts: wrong-credential `POST /api/auth/login` returns a normal 401 (backend reachable); preview login with valid creds returns 200 with 3 Set-Cookie headers.

## What I checked (production, active run 8ef824bf)
1. **Deploy/pod state** (`get_pod_events`): 2 pods Running, both `ready:true`, `restart_count:0`. No OOMKilled, no CrashLoopBackOff, no evictions. `kill_findings` empty.
2. **Worker lifecycle** (`fetch_app_logs`, per-pod, since deploy): each pod's uvicorn worker printed `Started server process` **exactly once** at boot (pid 25 on fqmnc, pid 24 on h5m8w). **No worker respawns, no SIGSEGV/SIGKILL, no "core dumped", no tracebacks.** A crash/empty-response origin bug would show a worker respawn here — none occurred.
3. **Request outcomes** (per-pod access logs, full post-deploy window): zero 5xx. A **complete real-user session post-deploy** (user `rajukhatana28@gmail.com`, Cloudflare client IP 162.159.102.141, 12:01:26–12:01:38 UTC) returned 200 on **every** request:
   - `POST /api/auth/login` → **200**
   - `GET /api/auth/me` → 200
   - `GET /api/wallet`, `/api/public/config`, `/api/contest/unseen-wins` → 200
   - `GET /api/live/favourites`, `/api/live/popular`, `/api/live/recent`, `/api/live/games` → **200** (the new live endpoints)
   - `GET /api/terms/status`, `/api/transactions`, `/api/banners/active` → 200
   The client received the login 200 and proceeded to authenticated calls — i.e. the login response (with its Set-Cookie headers) was delivered intact *through the real Cloudflare path* for this user.
4. **DB corroboration** (`mongo_query` users): `last_login_at` for that user = `2026-11-13T12:01:28` (post-deploy), confirming the login handler ran to completion and the response went out.
5. **Set-Cookie size** (source review, `backend/core.py`): login sets exactly **2** cookies — `access_token` and `refresh_token`, both short HS256 JWTs (~200–300 bytes each), `HttpOnly; Secure; SameSite=None; Path=/`. No third cookie is set by prod code (the "3rd" in preview is the preview-platform cookie, not present in prod). This is nowhere near Cloudflare's response-header limits → the **oversized/malformed Set-Cookie hypothesis is disproven**.
6. **New-code risk review**:
   - `backend/bulkapi.py` reads `os.environ["BULKAPI_BASE_URL"]` and builds `Fernet(sha256(JWT_SECRET))` **at import**, and is imported at the top of `server.py`. If `BULKAPI_BASE_URL` were missing this would KeyError and CrashLoop the pod at startup — pods are healthy and serving, so **both env vars are present and this import is not crashing the app**. Fernet key is derived via `urlsafe_b64encode(sha256(...))`, so it is always a valid 32-byte key regardless of `JWT_SECRET` content.
   - New Mongo indexes on `live_sessions/live_callbacks/live_rounds` are built in a background task with per-index try/except; no startup failure logged; the live endpoints all return 200.
   - `openpyxl`/`referrals.py` changes are not on the login path and showed no errors.
7. **Live edge probes** (now): `GET /` → 200 (correct Scarmenta SPA HTML), `GET /api/public/config` → 200 JSON. `list_domains`: both `scarmenta.com` and `www.scarmenta.com` verified, `ssl_status: active`.

## Root cause
**No backend fault is reproducible.** Login (`POST /api/auth/login` → 200) and every post-login call the user listed as a candidate (`/api/auth/me`, `/api/live/*`, wallet, banners, the page load) all return 200 in production, with zero 5xx, zero worker crashes/restarts, zero OOM, both pods Ready, and a full real post-deploy session completing cleanly. The cookies set are 2 small JWTs — not oversized or malformed. The live edge currently serves 200 for both the frontend and `/api`.

A Cloudflare 520 "could not parse response" requires the origin to return something empty/unparseable. The k8s backend demonstrably did **not** (no crash → no worker respawn; every logged response is a well-formed 200). The evidence is therefore most consistent with:
- **(a) A transient edge/origin gap during the rollout/promote window** (~11:55–11:57 UTC): promote flipped traffic at 11:56:30 while the second pod's image pull (~1m32s) was still completing — a brief window where an origin fetch could fail at the edge. This matches "right after the latest deploy" and is now cleared.
- **(b) If it is still recurring for specific users/browsers,** it is a **Cloudflare edge / Worker / R2-frontend layer** condition (the `cloudflare` frontend serves the SPA from R2 and a Worker proxies `/api`), not the app — because the origin backend returns clean 200s.

## Which request fails / pods crashing / header problems — direct answers
- **Which request fails:** none in production logs. login, `/api/auth/me`, and all `/api/live/*` return 200. `/api/popups` is not a route in this app (would be a parseable 404, not a 520).
- **Pods crashing/restarting/OOM:** no. 2 pods, restart_count 0, one worker start each, no OOM/CrashLoop.
- **Response header problems (oversized/malformed Set-Cookie):** none observed. 2 short JWT cookies; no custom header middleware; a real user's login response passed through Cloudflare and was accepted.
